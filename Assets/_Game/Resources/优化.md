## 一、架构级问题

### 1. EliminateCardController 上帝对象 — 2690 行

纯 C# 控制器承担了消除逻辑、卡牌状态机、Combo、道具效果、复活恢复、分数结算等至少 6 个职责。没有 partial class 拆分，单文件 87KB。

**建议**：拆为 `EliminateCardController.Core.cs`、`EliminateCardController.Combo.cs`、`EliminateCardController.Prop.cs`、`EliminateCardController.Resurgence.cs`。

### 2. EliminateTheAreaEntityLogic — 1927 行

实体逻辑脚本同时管理等待区渲染、分数精灵、卡牌拖拽、特效触发。职责过重。

**建议**：按功能域拆 partial class。

### 3. GameAssetModule — 1764 行

资源加载模块没有 partial class，资源缓存、预制体管理、Sprite 加载全部混在一起。

**建议**：拆为 `GameAssetModule.Cache.cs`、`GameAssetModule.Prefab.cs`、`GameAssetModule.Sprite.cs`。

### 4. PlayfieldEntityModule — 1506 行

场地实体管理模块，宠物站位、投影同步、标记点快照全部在一个文件。

**建议**：拆为 `PlayfieldEntityModule.Marker.cs`、`PlayfieldEntityModule.Snapshot.cs`、`PlayfieldEntityModule.Placement.cs`。

### 5. GameEntry 静态上帝入口 — 无 DI、无测试性

`GameEntry.CustomComponents.cs`（71 行）中所有模块都是 `static` 属性，业务层到处硬编码 `GameEntry.Fruits`、`GameEntry.DataTables` 等。无法做单元测试替换，无法控制生命周期。

**现状**：框架组件（`GameEntry.BuiltinComponents`）与自定义模块（纯 C# `new` 出来的对象）混在同一入口，初始化顺序靠代码行序隐式保证。

### 6. EliminateCardController.Instance 静态单例

纯 C# 对象用 `static Instance` 暴露，生命周期靠 `RebuildPreview` 赋值 / `Dispose` 清空。任何代码随时可访问，null 时 NRE 无防护。

### 7. 模块初始化模式不一致

`GameEntry.CustomComponents.cs` 中：
- `EntityIdPoolComponent`、`EggHatchComponent`、`PetDiningOrderComponent` → `GetComponent`（MonoBehaviour）
- `GameDataTableModule`、`GameAssetModule`、`PlayerRuntimeModule` 等 → `new`（纯 C#）

两类模块的生命周期管理完全不同：MonoBehaviour 跟随 GameObject，纯 C# 对象没有 `OnDestroy`/`Dispose` 退出路径。

## 二、违反架构标准

### 8. Addressables 与 Resources.Load 双后端自动透明接入（已落地）

GF 内核 `ResourceManager.ResourceLoader.LoadAsset` 入口注入了 Addressables 路由委托，**业务侧完全无需关心**资源在哪个后端 —— 资源在 Addressables 群组就走 Addressables，否则走 Resources.LoadAsync。

**自动路由通道（默认）**：

- `GameEntry.UI.OpenUIForm(...)` / `GameEntry.Entity.ShowEntity<...>` / `GameEntry.DataTable.LoadDataTable<...>` / `GameEntry.Sound.PlaySound(...)`
- `GameEntry.Resource.LoadAsset(...)` / `GameEntry.GameAssets.TryLoadAsset(...)`
- 底层链路：GF `ResourceComponent.LoadAsset` → `ResourceManager.ResourceLoader.LoadAsset` → **同步 `Addressables.ResourceLocators.Locate` 判定**：
  - 命中 Addressables 群组 → `Addressables.LoadAssetAsync<UnityEngine.Object>` → 登记反查表 → 按 `LoadAssetCallbacks` 协议派发
  - 未命中 → 走原 `ResourceMode.Resource = 4` + `ResourcesLoadResourceAgentHelper` → `Resources.LoadAsync`
- 释放：`HybridResourceHelper.Release` 反查 `s_HandlesByAsset` 字典精确释放 Addressables 句柄，未命中走 base.Release（Resources 资源行为）

**强制 Addressables 通道（扩展方法）**：

- `GameEntry.Resource.LoadAddressableAssetAsync<T>(...)` / `LoadAddressableAssetsAsyncByLabel<T>(...)` / `UnloadAddressableAsset(...)`
- 实现位置：`Assets/_Game/Script/Models/Asset/ResourceComponentExtensions.cs`
- 不经过 GF 内核路由，直接调 Addressables；适合业务侧明确需要 Addressables 能力（如 Label 批量加载）时使用
- `GameAddressableAssetModule` 对外 API 不变，内部全部收敛到扩展方法

**改造文件清单**：

GF 内核（第二波改造）：
- `Assets/GF/GameFramework/Resource/AddressablesAssetRouter.cs`（新增委托类型）
- `Assets/GF/GameFramework/Resource/IResourceManager.cs`（接口加 `SetAddressablesAssetRouter`）
- `Assets/GF/GameFramework/Resource/ResourceManager.cs`（字段 + setter + internal 访问器）
- `Assets/GF/GameFramework/Resource/ResourceManager.ResourceLoader.cs`（`LoadAsset` 入口加路由判定）

项目层：
- `Assets/_Game/Script/Models/Asset/AddressablesAssetRouterImpl.cs`（路由实现 + `BeginInitialize` 启动入口）
- `Assets/_Game/Script/Models/Asset/HybridResourceHelper.cs`（重写 `Release` 反查 Addressables 句柄）
- `Assets/_Game/Script/Models/Asset/ResourceComponentExtensions.cs`（暴露 `RegisterAddressablesHandle` / `TryReleaseAddressablesHandle` 静态 API）
- `Assets/GF/MyGameFramework.prefab`（`m_ResourceHelperTypeName: HybridResourceHelper`）
- `Assets/_Game/Script/Models/GameEntry.cs`（`Start` 改为 `BeginInitialize → OnAddressablesReady → InitCustomComponents`）

**仍直接调用 `Resources.Load` 的位置**（历史代码）：

- `WaitingAreaScoreSpriteRenderer.cs` / `ScoreDigitRenderer.cs`
- 后续如需改造，建议切到 `GameEntry.GameAssets.TryGetXxx` 命中预加载缓存。

**迁移路径**：把 `Resources/` 资源搬到 Addressables 群组时，业务方 **零代码改动** —— 路径字符串完全保留，加载链路自动从 Resources 切到 Addressables。

详细文档见 `Assets/GF/Docs/01_修改的GF与模块用法.md` §11、`Assets/GF/Docs/02_GF框架详细中文架构图.md` §7。

### 9. AdvertisementModule 闭包 + 字符串插值产生 GC

回调中使用 `$"[AdvertisementModule] 预加载失败：{err?.errMsg}"` 字符串插值，每次触发都分配。`OnLoad`/`OnError` 注册的 lambda 也是闭包，捕获了实例字段。

## 四、其他问题

### 17. VictoryFailUIForm / DailyChallengeUIForm 直接访问框架内部

```csharp
currentProcedure.procedureOwner.SetData<VarInt32>(...);
currentProcedure.ChangeState<MainProcedure>(currentProcedure.procedureOwner);
```

`procedureOwner` 是 `ProcedureBase` 的内部属性，业务层不应直接访问。2 个 UI 文件存在此问题。

### 18. PropPurchaseUIForm 的 static 事件 + static 状态

`s_purchasedThisBattle` 和 `OnPropPurchased` 都是 static。如果异常退出未走 `ResetBattlePurchaseState`，下一局会继承脏状态。static 事件也容易因订阅方未反订阅而泄漏。
